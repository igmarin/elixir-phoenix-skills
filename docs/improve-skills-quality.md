## Why this document exists

`report.md` (repo root, gitignored, regenerated by SkillSpector v2.1.4 — **not checked
into the repo**, and not to be hand-edited or deleted) flagged this repository at
**95/100 CRITICAL / DO NOT INSTALL**.
That score comes from a security scan of *agentic skill risk categories*, not a general
code-quality audit. This document is the working plan and tracker for:

1. Remediating the 8 SkillSpector findings and hardening `.github/review-prompt.md` so CI
   catches these categories going forward (and documents known false positives so they
   aren't re-flagged forever).
2. A deliberate Elixir/functional-programming depth pass across all 46 skills, run with the
   same rigor and rs-guard gating as the security fixes.

Every change lands through the sequence below: stage → run
`rs-guard --diff-file <diff> --prompt-file .github/review-prompt.md` for real (DeepSeek,
per `.reviewer.toml`) → iterate until the verdict is `APPROVE` with no blocking issues →
open PR. Nothing is pushed with an outstanding blocking rs-guard finding.

**Disposition:** all 8 are false positives, but every one is false-positive *because the
scanner's heuristics are reasonable* — the docs use real-looking hostnames, action verbs
("send", "query", "track"), and the word "tool" without disambiguating that this is static
Elixir/Phoenix teaching material, not agent-executable code. The fix is to remove the
ambiguity at the source (Section "Remediation approach" below) and to encode the
distinction permanently in `.github/review-prompt.md` (PR #1) so future skills don't
reintroduce it and so a real finding isn't dismissed by habit.

### Remediation approach (applied in PR #2)

- Replace ad-hoc example hosts (`api.your-app.test`, `*.test`) with IANA/RFC 2606-reserved
  documentation domains (`example.com`, `api.example.com`) everywhere in the skill library,
  not just the flagged file — this is a blocking rule in the new guardrail section.
- Reword the `refactor-code` context-boundary example to describe the action in
  non-ambiguous terms (e.g. "delegates welcome-email delivery to the Mail context")
  without changing the code sample's correctness.
- Reword the `deployment-gotchas` health-check pitfall row to make clear this is a
  read-only liveness check pattern, not an autonomous write/delete action.
- Reword the `liveview-streams` DevTools instruction to explicitly say "open your browser's
  DevTools" (human action, human tool) rather than an unqualified "DevTools" reference.
- Reword the `phoenix-channels-essentials` pitfall row to make the authorization check read
  as a guard clause, not a decision to perform a destructive action.

## Elixir/FP quality checklist (applied to every skill, all 46)

Beyond the existing structural "quality contract" (RULES section, Integration table,
Common Pitfalls contrast pairs — already enforced by `review-prompt.md` sections 1-2),
each skill gets evaluated/deepened against:

- **Immutability & rebinding** — no examples imply in-place mutation of structs/maps/lists.
- **Pattern matching depth** — multi-clause functions, guards, and binary/struct pattern
  matching are preferred over conditionals wherever the domain allows it.
- **Pipes & `with`** — pipelines read left-to-right without intermediate rebinding noise;
  fallible chains use `with`, not nested `case`.
- **Enum vs Stream** — skills touching collections call out when `Stream` (laziness) is the
  correct choice over eager `Enum` (large/infinite collections, composed transformations).
- **Recursion** — where relevant (parsers, tree/graph structures), skills show recursive,
  accumulator-based, or `Enum.reduce`-based solutions instead of manual index loops.
- **Protocols & behaviours** — polymorphism examples prefer `defprotocol`/`@callback`-based
  behaviours over conditional dispatch on type tags, where idiomatic.
- **"Let it crash"** — no defensive `try/rescue` used as control flow for expected,
  matchable failure states.
- **Supervision correctness** (OTP-adjacent skills) — restart strategies and process
  ownership match the "let it crash" philosophy already established in `elixir-essentials`.
- **Credo/Dialyzer alignment** — `@spec`/`@type` guidance is consistent with
  `typespec-dialyzer`, and no example would trip a default Credo check.

### Per-PR workflow (repeated for every row above)

1. Create a branch off `main` for the PR's scope.
2. Make the content edits (security fix and/or FP/quality checklist) for every skill in
   scope.
3. `git add` the changed files (staged, not committed) and generate a diff:
   `git diff --cached --unified=5 > /tmp/rs-guard-<scope>.diff`
4. Run `rs-guard --diff-file /tmp/rs-guard-<scope>.diff --prompt-file .github/review-prompt.md`
   for real (no `--dry-run`) and read the verdict.
5. If `REQUEST_CHANGES` or any blocking issue: fix, re-stage, re-run step 4. Repeat until
   `APPROVE`.
6. Commit, push, open the PR, and record the rs-guard verdict + iteration count in the
   table below.
7. Update this document's status column to `merged` once the PR lands.
